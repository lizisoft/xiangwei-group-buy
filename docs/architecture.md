# 社区团购架构

系统只有一个社区团购领域。API 服务按能力拆分为认证与员工、目录与团期、订单、支付退款、配送领取、通知、账本和审计；领域服务只依赖所需的窄存储能力。

## 关键一致性

- 订单创建在同一事务中锁定团期可售量、写订单明细和幂等记录。
- 支付回调以事件号和正文摘要去重，订单支付与取消/截单通过条件状态更新竞争。
- `REFUNDING` 转换与唯一退款义务（固定 `providerRefundNo`）在同一数据库事务持久化；退款调和扫描只消费已提交的义务，绝不以事务外数组或内存 Promise 首次创建退款。
- 退款提交使用租约和认领令牌，迟到的支付机构响应不能覆盖新处理者。退款记录必须表达待提交、提交结果未知、支付机构处理中、可重试失败、人工挂起和成功这六种逻辑状态（可由状态与重试/租约字段等价表达）。
- 调和以同一 `providerRefundNo` 查询或安全重提：提交前失败可重试；提交后响应丢失先查询；未找到、5xx 或超时在租约到期后按退避重试，到达上限转人工处理而非永久停留在处理中。全额和部分退款使用同一恢复语义；成功落账、订单/支付状态变更和迟到回调均为一次性条件更新。
- 到货差异先保存现场事实，再按 `paidAt ASC, orderNo ASC` 生成草案；运营确认后才开放正常数量领取并允许财务退款。
- 核销以领取请求号和内容摘要幂等，订单明细在事务内更新，支持分次领取。
- 通知使用事务内 outbox，提供方失败重试后进入人工联系队列；人工完成保存外部渠道证据，未知提交结果不得自动重复外发。
- 员工状态和点位范围在每次敏感操作校验；变更时删除现有会话。
- 周期调和在单实例内禁止重入，生产 Redis 以带过期时间的租约选出一个运行者；API 副本未拿到租约时跳过本轮。调和失败会使执行副本 readiness 降级，详细错误只写脱敏日志。当前健康状态保存在副本内存，非持锁副本不能据此证明全局调和健康，因此多副本发布前必须引入共享 last-success/error 信号或将任务拆到独立 worker；本轮仅接受受控单副本试点。

## TASK-REM-P0 验收契约

- 退款故障恢复必须可重放：事务提交后、外部提交前的进程中断，重启调和后应只创建并提交原退款义务一次；支付机构收到请求但响应丢失时，调和只能使用原退款单号查询/重提。
- 到货确认入口按角色和点位范围二次校验，不能只依赖前端隐藏。`PICKUP_MANAGER` 有已授权点位的正常提交权，`OPERATOR` 没有该权，`SUPER_ADMIN` 的紧急代办必须有原因并进入审计。

## 数据基线

`0001_community_baseline.sql` 是早期尚无正式交易数据时建立的新库基线；这是迁移设计的历史背景，不代表当前正式环境没有数据，也不构成清库或覆盖数据库的依据。迁移不写入演示数据，也不写入任何具体城市或点位。数据库迁移按文件名依次执行，并核对已执行文件的校验和。0005 建立实体表和迁移状态，初始模式为 LEGACY。DDL、数据准备与激活是不同步骤。见[迁移入口](../apps/api/src/scripts/migrate.ts)和[实体迁移](../infra/mysql/migrations/0005_entity_store.sql)。

MySQL 适配器读取数据库中的模式。LEGACY 使用单行 JSON 聚合，PREPARED 是迁移过渡态，ENTITY 按实体记录读取并持久化变更。业务写事务仍先取得同一全局行锁。评估容量时应记录实际模式、数据规模、锁等待和请求时延，并在对应模式验证恢复能力。[存储实现](../apps/api/src/modules/core/mysql-store.ts)

2026-09-28 的[发布记录](task-20260928-overall-optimization.md)记载当时已激活 ENTITY。此后发布或迁移前，按目标环境重新确认模式与恢复路径。

新库按迁移目录初始化。已有业务库升级前核对当前结构、迁移记录、备份和恢复路径；遇到未知旧表时保留原库，在隔离库验证迁移。

应用启动不得生成“全国默认自提点”或任何伪履约数据；消费者公开区域必须至少关联一个真实启用点位。
